### Role Contributor — JSON (bước 4)

Đường dẫn: Subscription → Access control (IAM) → Roles → Contributor → View → JSON.

```json
"permissions": [{
  "actions": ["*"],
  "notActions": [
    "Microsoft.Authorization/*/Delete",
    "Microsoft.Authorization/*/Write",
    "Microsoft.Authorization/elevateAccess/Action",
    "Microsoft.Blueprint/blueprintAssignments/write",
    "Microsoft.Blueprint/blueprintAssignments/delete",
    "Microsoft.Compute/galleries/share/action",
    "Microsoft.Purview/consents/write",
    "Microsoft.Purview/consents/delete",
    "Microsoft.Resources/deploymentStacks/manageDenySetting/action",
    "Microsoft.Subscription/cancel/action",
    "Microsoft.Subscription/enable/action"
  ],
  "dataActions": [],
  "notDataActions": []
}]
```

Đọc hiểu:

| Trường | Giá trị | Nghĩa là |
|---|---|---|
| `actions: ["*"]` | mọi thao tác control plane | Tạo, sửa, xoá mọi loại resource |
| `Microsoft.Authorization/*/Write` và `/*/Delete` | bị trừ | **Không tạo/xoá được role assignment** → không cấp quyền cho ai (kể cả cho managed identity) |
| `Microsoft.Authorization/elevateAccess/Action` | bị trừ | Không tự nâng mình lên quyền cao hơn |
| `Microsoft.Subscription/cancel` / `enable` | bị trừ | Không huỷ hoặc bật lại subscription |
| Blueprint, Purview consents, deploymentStacks deny setting, gallery share | bị trừ | Các thao tác mang tính quản trị/chia sẻ ra ngoài |
| `dataActions: []` | rỗng | **Không có quyền data plane nào**: không đọc secret Key Vault, không pull/push ACR bằng RBAC data role, không đọc blob bằng Entra ID |

**Kết luận cho dự án:**
1. Nếu danh tính chạy Terraform chỉ là Contributor, bước tạo role assignment (AcrPull, Key Vault Secrets User cho MI) sẽ bị từ chối → cần thêm quyền cấp phép (User Access Administrator hoặc Role Based Access Control Administrator giới hạn scope), hoặc Owner ở scope hẹp.
2. Contributor tạo được Key Vault nhưng không ghi được secret vào vault ở chế độ RBAC, vì `dataActions` rỗng.
3. Owner khác Contributor đúng ở chỗ Owner không có dòng trừ `Microsoft.Authorization/*` — nhưng `dataActions` của Owner **cũng rỗng**.

## Khái niệm

### Tenant, subscription, resource group
- **Tenant** (Microsoft Entra ID): nơi chứa danh tính — user, group, app registration, managed identity. Tài khoản `@vinuni.edu.vn` thuộc tenant VINACADEMY LLC.
- **Subscription**: vừa là đơn vị tính tiền, vừa là ranh giới quyền và quota. Mọi resource phải thuộc một subscription.
- **Resource group**: thư mục gom resource **có cùng vòng đời**. Xoá RG = xoá mọi thứ bên trong. Vì vậy storage chứa Terraform state (sống lâu) không để chung RG với app (dựng/xoá hằng ngày).

### Control plane và data plane
- **Control plane** — quản lý resource qua Azure Resource Manager (`management.azure.com`): tạo, xoá, đổi cấu hình. Quyền nằm ở `actions`.
- **Data plane** — dùng dữ liệu bên trong resource qua endpoint riêng (`<vault>.vault.azure.net`, `<registry>.azurecr.io`, kết nối MySQL): đọc secret, pull image, chạy SQL. Quyền RBAC nằm ở `dataActions`.
- Bằng chứng từ JSON Contributor ở trên: `actions` = `*` nhưng `dataActions` rỗng.
- Firewall/network rule của Key Vault, ACR, MySQL chặn data plane; control plane vẫn quản lý được.

### RBAC
- Mỗi role assignment = **Ai** (security principal: user, group, service principal, managed identity) + **Làm gì** (role definition: actions, notActions, dataActions, notDataActions) + **Ở đâu** (scope: MG / subscription / RG / resource).
- Không có assignment → **mặc định bị cấm**.
- Quyền **kế thừa xuống** các scope con và **cộng dồn** khi có nhiều role.
- Quyền hiệu lực = `actions` trừ `notActions` (tương tự cho data). `notActions` không phải "deny" — nếu một role khác cho phép thao tác đó thì vẫn làm được.
- Assignment mới có thể mất **vài phút** mới có hiệu lực → nguồn lỗi "vừa apply xong app vẫn 403".
- **Least privilege**: role nhỏ nhất, scope hẹp nhất.

| Role | Plane | Dùng trong dự án |
|---|---|---|
| Owner | Control | Tài khoản của tôi hiện tại |
| Contributor | Control | Không đủ nếu cần tạo role assignment |
| Reader | Control | Chỉ xem |
| User Access Administrator | Control | Chỉ cấp quyền |
| AcrPull | Data | MI pull image từ ACR (M1) |
| Key Vault Secrets User | Data | MI đọc secret (M4, M5) |
| Key Vault Secrets Officer | Data | Người/Terraform ghi secret |

### Managed Identity
- Danh tính do Azure cấp cho resource; app xin token từ endpoint nội bộ, **không có mật khẩu** trong code hay app settings.
- **System-assigned**: gắn chặt một resource, xoá resource là mất. Mỗi deployment slot có identity riêng → khi swap, code mới chạy bằng identity khác, dễ thiếu quyền.
- **User-assigned**: resource độc lập, gắn được cho nhiều resource → dự án dùng loại này, gắn cho cả slot production và staging.
- **Service principal**: danh tính cho thứ chạy **ngoài** Azure (GitHub Actions). Dùng kèm OIDC ở tuần 2 để không lưu client secret.

## Câu hỏi tự kiểm tra

1. **Owner có tự đọc được secret trong Key Vault (RBAC mode) không?**
   Không. Owner chỉ có `actions` (control plane); đọc secret là `dataActions`, cần thêm Key Vault Secrets User/Officer.
2. **Vì sao cấp role ở RG thay vì subscription?**
   Least privilege: quyền kế thừa xuống, cấp ở subscription thì áp cho mọi RG kể cả thứ không liên quan (ví dụ storage chứa state).
3. **System-assigned identity + swap slot → chuyện gì xảy ra?**
   Hai slot có hai identity khác nhau; sau swap, code có thể chạy bằng identity chưa được cấp AcrPull/Key Vault → lỗi đúng lúc deploy.
4. **GitHub Actions dùng Managed Identity hay Service Principal?**
   Service principal + federated credential OIDC, vì runner GitHub không phải resource Azure của mình nên không có managed identity.
5. **Budget có tự tắt resource không?**
   Không, chỉ cảnh báo.
6. **Vừa gán role mà app vẫn 403 — nguyên nhân khả dĩ?**
   Quyền chưa lan truyền; token cũ còn cache; gán nhầm principal (system vs user-assigned) hoặc nhầm scope; network rule chặn data plane.
